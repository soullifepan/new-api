# APIMart 合作伙伴活动页研究与 TapComfy 设计讨论材料

日期：2026-09-29
状态：研究稿，供讨论；不是已批准的实现规格
工作分支：`codex/feature/partner-referrals`
代码核对基线：`a5a0e8b3c`

## 1. 研究目的与证据范围

研究 APIMart 如何组织合作伙伴申请、审核通过后的推广工具、邀请统计及奖励使用入口，为 TapComfy 的客户端体验和配套后台设计提供依据。本轮只整理文档，不实现页面、接口、数据库或支付流程。

### 1.1 来源编号

| 编号 | 来源 | 能确认的范围 |
| --- | --- | --- |
| H1 | 用户提供的第 1 段 HTML：邀请赚奖励 | 未申请页面、招募文案、禁用统计、参与步骤 |
| H2 | 第 2 段 HTML：申请弹窗 | 初始表单、可见字段、HTML 属性、抽屉布局 |
| H3 | 第 3 段 HTML：申请通过后的页面 | 推广码、分享入口、9 行邀请统计、划转按钮 |
| S1–S4 | 同一会话之前的 4 张截图 | 页面外观、申请抽屉上下部分、通过后页面 |
| W1–W3 | 后续补充的 3 张截图：对私提现、对公提现门槛、美元额度划转 | 另一套人民币收益的提现与额度兑换界面；背景可见 `yunwu.ai`，不归为 APIMart 的已验证能力 |

| U3 | 用户逐项确认“都支持”“同意”“申请只是个门槛……按需补充。其他推广方式也行” | 两种收益出口、老邀请客户后续充值返佣、不追溯历史、申请证明按需补充 |
| U4 | 用户确认“当然要支持 2 种啊，对私很受限制的” | 首版同时支持对私支付宝与对公账户提现 |
| U5 | 用户要求“现阶段肯定是独立打款。先做记录……转账完成后，把申请点了，把金额结算掉” | 首版做人工提现台账，站外独立付款，后台标记已打款并结算；不接自动付款接口 |
| U6 | 用户明确“newapi 主要提供接口，给 tapcomfy 客户端去实现……主要在 admin 和后端” | 用户页面在 TapComfy；new-api 承担后端业务、API 和管理员页面 |
| U7 | 用户明确“不用显示总消耗和消耗次数……重要的是看到下面的用户充值了几次，充值了多少” | 合作伙伴邀请列表以每位客户的充值次数与累计充值为重点，不提供消费统计 |
| C1 | 当前 new-api 仓库的只读检查 | 已有邀请码、邀请奖励、钱包、充值与订阅能力 |

这些是用户提供的页面快照，没有执行 APIMart 页面脚本、点击按钮、提交申请或调用其接口。HTML 中的按钮、文案、样式和属性不能证明服务端行为。截图与 HTML 也不必然来自同一个构建版本。

本文用“观察”表示材料直接可见；“推断”表示合理解释但尚未验证；“待讨论”表示 TapComfy 可以采用的候选设计。未展示某项能力，不等于 APIMart 没有该能力。

不原样存入用户昵称、完整个人推广链接或整段营销文案；表格使用 A–I 匿名标识，保留研究所需数值。本文没有把材料中的产品数量、价格优势和模型支持宣传当作已核实事实。

### 1.2 当前最重要的边界

1. 参考流程是“申请 → 审核通过 → 获得推广工具 → 邀请注册 → 客户充值 → 获得奖励”。
2. 展示规则为注册后一年内每次充值返 10%，不是仅首充返佣。
3. H3 的资金按钮原文为“划转余额”，不是“提现”。用户把这一页称为“邀请记录 + 提现”，本文保留这个业务意图，但尚不能确认 APIMart 的外部现金付款能力。
4. U1 的换算只用于解释 APIMart 样例；TapComfy 是否采用同一 Credits 比例尚未确定。
5. TapComfy 的比例和返佣期限需要可配置，不能照抄 10% 和一年并写死。返佣固定覆盖有效期内每次充值，不提供仅首充模式。
6. U3 已确认 TapComfy 同时支持现金提现和转入消费余额。W1–W3 是新增的提现参考，不改变 H3 只提供划转入口这一证据边界。

## 2. 未申请页面（H1）

### 2.1 页面结构与顺序

| 顺序 | 区域 | 内容与作用 |
| --- | --- | --- |
| 1 | 页标题 | “邀请赚奖励”，副标题说明分享推荐链接获得奖励 |
| 2 | 联盟招募卡 | 面向 YouTube、X/Twitter、TikTok 创作者和 KOL；说明每笔充值 10% 佣金；右侧“立即申请” |
| 3 | 统计卡 | 总邀请数、总充值、总返现、可划转余额；均显示零 |
| 4 | 邀请好友链接 | 只读文本提示先申请、审核通过后获得专属链接 |
| 5 | 如何运作 | 六个步骤说明参与和奖励规则 |

统计卡容器有 `pointer-events-none select-none opacity-50 grayscale`，表现为功能预览。这里只能确认前端视觉和交互样式，不能据此认定服务端已限制未获批用户访问相关数据。

H1 不展示推荐码、复制按钮、邀请统计表或划转操作；“邀请好友链接”区域仍占位，让用户理解获批后会获得什么。

### 2.2 六步规则的准确含义

| 步骤 | 页面表达 | 研究结论 |
| --- | --- | --- |
| 提交申请 | 填写推广大使申请信息 | 加入合作计划有申请门槛 |
| 申请通过 | 管理员审核；获得推广链接和后台访问权限 | 存在人工审核语义；“后台”不能理解成管理员权限 |
| 邀请好友注册 | 分享专属链接；“注册即可开始获得返现” | 文案不够精确，应结合后续充值条件理解 |
| 首次充值 | 任意金额首充，获得 10% 返现 | 首充开始产生奖励；未说明支付渠道最低充值额 |
| 返现期限 | 好友注册后一年内每次充值都返 10% | 持续返佣，起算点的文案是好友注册时间 |
| 无上限奖励 | 邀请人数不限 | 明确的是邀请人数不限；不能推导提现金额、频率或单笔额度不限 |

HTML 没有显示比例或期限的配置入口，不能判断 APIMart 能否对不同合作伙伴采用不同规则。“一年”是 365 天还是按自然年计算、到期边界和时区均未知。

## 3. 申请抽屉（H2）

### 3.1 容器与交互结构

- 右侧 Sheet，`role="dialog"`，标题和描述通过 `aria-labelledby` / `aria-describedby` 关联。
- 标题“申请加入推广计划”，描述“目前我们仅接受以下类型的申请”。
- 中间内容区独立滚动；底部取消、提交申请按钮位于滚动区之外。
- 右上角关闭按钮，屏幕阅读器文本为英文 `Close`。
- 样式含全高、`w-full`、`sm:max-w-[700px]`，同时保留 Sheet 原语的侧边宽度类；没有最终 CSS 和运行时测量，不断言实际宽度恰好为 700px 或移动端必定全屏。
- 截图展示了抽屉背后的遮罩效果，但未提供遮罩 DOM。

可确认有取消、关闭、提交入口，不能确认点击遮罩、按 Escape 是否关闭，焦点是否循环、关闭是否保留草稿、提交后如何提示。

### 3.2 字段清单

| 字段 | 必填标记 | 观察到的控件与约束 | 尚未确认 |
| --- | --- | --- | --- |
| 推广渠道 | 有 | 两列复选框，共 14 项 | 最少选几项、选择“其他”是否出现额外输入 |
| 账号链接 | 有 | 初始 1 个输入框；示例为 YouTube URL；可添加另一个链接 | 上限、删除交互、去重、URL 校验、与渠道的对应关系 |
| 推广计划 | 有 | 文案建议 50–500 字；`minlength=50`、`maxlength=500`；右下角 `0 / 500` | 服务端是否强制最短长度、Unicode 计数、空白处理 |
| 账号证明截图 | 有 | 文件选择控件；提示 JPEG/PNG/WebP，最大 10MB | 实际 MIME/体积验证、预览、替换、删除、上传失败行为 |
| 联系信息 | 有 | 单个文本输入；示例支持邮箱、Telegram 用户名或微信 ID | 类型识别、格式校验、是否支持多个联系方式 |
| 补充说明 | 无 | 多行文本，最小视觉高度约 100px | 最大长度、敏感信息提示 |

“必填”指星号标记。字段大多没有原生 `required`；提交按钮为 `type="button"`，片段也未展示原生表单提交。因此不能仅凭星号和 `minlength` 宣称已具备实际校验。

推广计划初始计数使用危险色，输入区最小高度约 150px。说明中的“建议”与 HTML 最小长度约束存在表达差异，后续应统一为建议或强制要求。

### 4.1 与未申请页的变化

| 区域 | 未申请 | 审核通过 |

| 推广码 | 不展示 | 大号显示，可编辑 |

### 4.2 推广码和分享区

第一行由推荐码区域和“复制链接”按钮组成；第二行由“复制分享链接”按钮和只读分享文案组成。大屏使用一列自适应内容加 168px 固定操作列；复制按钮是 168px 方块。小屏取消双列布局，但按钮本身仍保留固定尺寸。

“编辑推荐码”入口存在，但没有编辑弹窗、保存结果、唯一性和长度规则。显示推荐码的元素使用 CSS `uppercase`，而文本和 URL 参数保留混合大小写：这只能证明显示转换，不能证明邀请码匹配大小写不敏感。

推广链接形态为 `https://apib.ai/register?aff=<推荐码>`。本研究不访问该个人链接。

第一个按钮大概率复制纯 URL，第二个大概率复制整段分享文案，但 HTML 没有事件处理函数，实际剪贴板内容尚未验证。第二个按钮的名称不足以明确区分两种行为；TapComfy 若采用，宜叫“复制邀请链接”和“复制推广文案”。

底部有 Twitter、Facebook 和邮件三个分享按钮。未见目标 URL、邮件主题、正文拼接和跳转方式；按钮存在不表示已验证社交平台分享流程。

分享文案是只读的，包含产品介绍和注册链接。其模型名称、数量及价格比较容易过时，不宜写入固定客户端业务代码，也不应把这段第三方营销文案直接用于 TapComfy。

### 4.3 邀请用户统计

表格列为：用户、总充值、总消费、总返现、充值次数、消费次数。金额右对齐，采用等宽数字；返现带正号和成功色。

表格最小宽度为 820px，外层允许横向滚动。没有提供搜索、排序控件、分页或导出入口。行数据按充值金额非递增排列，但不能由单次快照证明默认排序规则。

“查看全部记录”指向 `/zh/referral-history`。这是邀请记录页面路径；不能据此推导它展示的是提现记录、订单明细还是同一统计表的完整列表。

H3 顶部显示 15 个邀请，表格只有 9 行。可能是筛选、预览数量或业务口径差异，材料不足以判断另外 6 人是否未充值、被隐藏或被分页。

## 5. Credits 换算与样例对账

### 5.1 单位解释

按 U1：

```text
1 USD = 10 Credits
美元等值 = Credits ÷ 10
示例返佣率 = 10%
```

这里只做单位换算，不推断 Credits 可以按该比例无条件兑付现金；实际提现汇率、手续费、币种和门槛均未提供。

| 顶部指标 | HTML 数值 | 美元等值或说明 |
| --- | ---: | ---: |
| 总邀请数 | 15 | 人数，不换算 |
| 总充值 | 13,940.00 Credits | $1,394.00 |
| 总返现 | +1,394.00 Credits | $139.40 |
| 可划转余额 | 73.00 Credits | $7.30 |
| 总返现与可划转差额 | 1,321.00 Credits | $132.10；去向未知 |

总返现与总充值的比例为 `1394 ÷ 13940 = 10%`。不能把 13,940 Credits 当成 13,940 美元，也不能把 73 Credits 当成可提现 73 美元。

差额 1,321 Credits 可能涉及历史划转、待处理金额或其他调整，不能直接写成“累计已提现”。

## 6. 划转与现金提现：当前可确认到哪里

H3 的“划转余额”按钮具有 `data-slot="alert-dialog-trigger"`、`aria-haspopup="dialog"`、`aria-expanded="false"`，说明存在尚未打开的确认对话框入口。片段没有该对话框正文。

| 问题 | 当前证据 |
| --- | --- |
| 是否有奖励使用入口 | 有，名为“划转余额” |
| 是否要求二次确认 | 有确认对话框触发器，内容和执行过程未知 |
| 是否转入站内消费余额 | 名称支持此推断，但没有目标账户说明 |
| 是否支持外部现金提现 | 未提供对应表单、收款方式或打款记录 |
| 能否自定义划转金额 | 未知 |
| 是否全额划转、最小金额多少 | 未知 |
| 有无手续费、冻结期、审核 | 未知 |
| 是否有提现记录、失败重试 | 未知 |

因此需要分开使用三个概念：

- **佣金/奖励**：客户付费后归属于合作伙伴的收益。
- **转入消费余额**：把收益变成站内消费额度。
- **现金提现**：将收益支付到站外收款账户。

TapComfy 已确认同时支持后两种出口，并按 U5 采用站外独立打款、站内记录和结算。APIMart 的 H1–H3 仍只证明存在划转入口；W1–W3 补充了另一套提现和划转体验。TapComfy 的人工处理决定不能反推为这些参考产品的后台行为。

### 6.1 新增参考：人民币收益的对私提现（W1）

左侧资金摘要显示“本次最多可提 ¥33.54”“账户余额 ¥33.54”“今日剩余可提 ¥500.00”。右侧提现方式有“对公账户（推荐）”和“对私支付宝（小额）”，当前选中对私支付宝。

| 项目 | 可见内容 |
| --- | --- |
| 支付宝账号 | 必填输入，截图已有值；文档不保存该账号 |
| 真实姓名 | 必填输入，截图已有值；文档不保存该姓名 |
| 提现金额 | RMB，当前 33.54，支持“全部”入口 |
| 限额说明 | 对私单日累计提现不可超过 ¥500.00，超过提示切换对公 |
| 操作 | 提现说明、取消、提交提现、右上角关闭 |

本次最多可提与账户余额相等，低于今日剩余额度；与“取余额和限额中较小值”的设计一致，但截图不能证明后台公式。每日时区、处理中申请是否占用额度、拒绝后何时返还额度均未知。账号输入有值不能证明资料已校验或已持久保存。

### 6.3 新增参考：收益转入美元额度（W3）

该弹窗标题为“请输入要划转的美元额度金额”，展示：

### 9.1 不能直接复用为新业务口径的部分

**邀请人数。** 目前 `aff_count` 的增加位于固定邀请奖励路径，受奖励配置及现有开关影响。新页面若要显示真实邀请人数，需要明确从邀请关系统计，不能直接假定历史 `aff_count` 完整。

**历史奖励。** 现有 `aff_quota` 可能来自固定注册赠送。不能直接把它视为可现金提现的充值佣金；保留、迁移或分账需要单独定规则。

**实付金额。** `TopUp.Amount`、`Money` 在不同渠道有不同语义。例如 Stripe 写入的 `Money` 是 `GetChargedAmount` 的换算结果，并非由一个统一的实付币种字段定义。新佣金依据必须明确支付来源、实付金额、币种和换算快照。

**订阅重复记账。** `CompleteSubscriptionOrder` 会调用 `upsertSubscriptionTopUpTx`，将同一订阅订单同步为 `TopUp` 记录。因此不能在“订阅完成”和“发现充值成功记录”两个位置各发一次佣金；应按唯一支付业务事件识别来源和去重。

**余额买订阅。** `PurchaseSubscriptionWithBalance` 产生成功订阅订单，但没有新增外部付款。按本次“实际付款才返佣”的方向，已返佣的充值余额购买订阅不能再发一次佣金。未来若有其他业务规则，应显式定义，不依赖订单状态猜测。

**独立客户端范围。** U6 已明确用户端页面由 TapComfy 实现，new-api 的前端改动仅针对管理员功能。本次检查的是 new-api 仓库，未检查 TapComfy 独立客户端的组件和路由；实施前在对应仓库核对，不把 new-api 现有钱包卡片直接当成 TapComfy 组件。

### 9.2 后续需要补齐的业务能力

- 申请资料、审核结果、补充资料原因和申请历史。
- 合作伙伴资格及其当前生效规则。
- 邀请归属、资格起止时间和推广码更改规则。
- 按唯一支付事件产生的佣金明细与规则快照。
- 客户端概览、邀请客户列表、佣金明细和资金操作记录。
- 人工提现台账：申请、收款信息、金额占用、完成结算或驳回；备注和凭证作为辅助记录。

以上是能力清单，不是已经确定的数据表、接口路径或开发任务拆分。

## 10. 用于后续讨论的候选设计

### 10.1 客户端状态与页面

| 候选状态 | 页面重点 | 主要操作 |
| --- | --- | --- |
| 未申请 | 招募说明、资格、适用奖励规则 | 申请加入 |
| 审核中 | 申请时间、资料摘要、审核状态 | 查看申请；能否撤回/修改待定 |
| 待补充 | 缺失内容、审核意见 | 补充并提交 |
| 未通过 | 明确原因 | 是否允许重新申请待定 |
| 已通过 | 推广工具、邀请列表、收益与记录 | 复制链接、使用或提取佣金 |
| 已暂停 | 状态说明、已有收益及处理规则 | 联系处理；不能仅用置灰隐藏原因 |

只有“未申请”和“已通过”的参考页面有直接证据，其余是为闭环提出的设计候选。伙伴状态、申请状态和资金状态应分别表达，避免一个“已通过”同时代表审核、收益可用及付款完成。

获批页可以组织为“概览、推广工具、邀请客户、佣金明细、资金记录”。是否拆成标签页取决于数据量和客户端布局，不应现在固定。

#### 合作伙伴邀请列表（U7 已明确统计重点）

沿用参考页面的“邀请用户统计”，去掉总消耗和消耗次数。拟保留以下列：

| 列 | 含义 | 决策依据 |
| --- | --- | --- |
| 用户 | 区分受邀客户的标识 | 参考列表结构；显示/脱敏方式待定 |
| 累计充值 | 该客户在统计范围内成功充值的金额 | 用户明确要求，核心指标 |
| 充值次数 | 该客户在统计范围内成功充值的订单数 | 用户明确要求，核心指标 |
| 贡献佣金 | 该客户产生的佣金合计 | 保留参考页总返现列，便于伙伴对账 |

充值次数按成功订单去重，重复回调或管理员补单不能额外增加次数。未支付、失败订单不计入成功充值；赠送额度和内部划转不算充值。金额的币种或额度单位需要明确，不能只返回一个无单位数字。

充值统计与返佣资格分别计算：不能为了让金额乘比例等于佣金而隐藏真实充值记录。对老邀请客户，统计是否覆盖获批前历史、以及默认时间范围仍待确定；已经确定的是获批前充值不补发佣金。未来订阅付款的统计应明确区分类型，避免同步的充值记录被重复累计。

new-api 提供当前合作伙伴名下客户的分页充值汇总，TapComfy 负责列表展示。此接口无需查询或返回模型消费金额、调用次数与消费日志；用户也不需要为查看充值贡献而接触客户的模型使用情况。

### 10.2 配置范围

| 候选配置 | 可选方向 | 需要明确的语义 |
| --- | --- | --- |
| 充值返佣比例 | 管理员设置 | 实付金额基数；精度与舍入 |
| 充值次数范围 | 每次 | 有效期内每次真实充值，不提供仅首充选项 |
| 返佣期限 | 指定天数/长期 | 从注册、首付还是伙伴获批起算；到期边界 |
| 订阅返佣 | 开关及独立比例 | 外部支付首购、续费、升降级差额；避免余额支付重复返佣 |
| 规则层级 | 全局；可选伙伴覆盖 | 哪层生效、后台如何展示继承关系 |
| 结算等待期 | 即时可用/延迟可用 | 起算事件；与可提现状态分开 |
| 资金用途（已确认） | 同时支持转消费余额与现金提现 | 共用佣金余额，不可重复支取；兑换与撤销规则待定 |
| 提现规则 | 门槛、方式、费用、频率 | 单位、到账币种与收款信息 |

“规则可配置”已明确，具体配置项与默认值尚未全部确认。修改比例应保留历史订单账目；新规则影响既有客户的未来订单还是仅影响新客户，需要单独定义并在客户端准确说明。

### 10.3 归属与推广码

后续需要一起讨论：

1. 已确认既有邀请关系继续有效，仅获批后的充值纳入返佣、不追溯历史；仍需定义老客户的返佣期限起算点；不再提供首充模式。
2. 用户先后打开多个伙伴链接时，归属如何确定；链接保存有效期与返佣有效期是两个概念。
3. 老用户是否允许补绑定，绑定后能否更换邀请人。
4. 编辑推广码后，旧链接是否继续有效；是否允许旧码分配给其他人。
5. 暂停伙伴后，新邀请和既有受邀客户后续付款如何处理。

推荐码应指向稳定的伙伴身份，改码不应意外改变已有客户归属；这是候选原则，不是当前代码已经具备的能力。

### 10.4 首版提现流程（已确认采用人工台账）

首版只负责申请记录和资金结算。管理员独立使用支付宝或企业网银等渠道付款，付款完成后在后台处理对应申请。无需自动代付接口、支付回调、轮询付款状态或多级审批流。

```text
用户填写金额和收款信息 → 提交提现申请（待处理）
管理员查看申请 → 站外独立转账 → 后台点击“标记已打款” → 结算完成
无法处理的申请 → 填写原因并驳回 → 释放占用金额
```

界面保留“待处理、已打款、已驳回”三个基本状态。查看申请和核对资料合并在同一操作中，不额外设置“审核通过后等待另一级审批”等步骤。实际付款尚未确认时保持待处理，不能提前点击已打款。

申请提交时先占用对应佣金，避免同一余额重复申请或转入消费余额；标记已打款时，将占用金额转为已结算/已提现，不再重复扣一次。驳回则释放占用。这是台账的基础记账要求，不增加用户操作。重复点击“已打款”不能重复结算。

每条申请至少记录申请人、申请金额及币种、提现方式、提交时的收款资料、申请时间、状态，以及完成时的操作人和时间。转账流水号、付款凭证与备注可作为辅助信息，不默认强制上传凭证。两种提现方式共用这一流程，仅收款字段不同。

两种提现方式均为首版必需能力，下面是待讨论的字段与交互细化：

| 方式 | 建议收款资料 | 建议客户端展示 |
| --- | --- | --- |
| 对私支付宝 | 支付宝账号、收款人姓名 | 本次可提、单笔限额、今日剩余额度、预计到账金额 |
| 对公账户 | 企业名称、统一社会信用代码、开户行、对公账号；证明按需补充 | 收款账户、本次可提及对公适用限额 |

限额按方式分别配置，不把参考页面的对私每日 500 元和对公单笔 5000 元写死。对私额度不足时，可提示改用对公；切换方式后重新校验其资料与限额，但不能解除或绕过已提交提现占用的佣金。管理员付款前核对收款资料，不因合作资格通过就省略收款信息核对，也不新增独立认证系统。

客户端分别提供“提现”和“转入消费余额”，后者明确目标是消费额度。两种能力共享可用资金约束，防止同一笔佣金既划转又提现；提现申请冻结中的金额不能再划转。

### 10.5 最小管理端

客户端功能至少需要对应的管理能力：审核申请、查看证明资料、给出通过/补充/拒绝意见、设置规则、暂停资格、查看佣金来源。现金提现还需要审核和付款登记。

申请资料与收款资料不应公开展示给其他伙伴；统计接口按当前伙伴身份限制访问。上传资料的存储、权限、类型/体积限制和保留时间需要随实现一起确定。金额计算、审核资格、重复支付通知和重复点击的防重均应由服务端保证。

这些是后续设计的约束，本文不引入新的权限实现、不认定现有接口已满足它们。若实施触及数据库，需要按项目规则完成真实 SQLite/MySQL/PostgreSQL 验证。

### 10.6 仓库职责与现有代码接入边界

U6 已确认客户端与后台分工。下面的模块组织是建议实现方向，尚未创建任何文件或接口。

| 所属部分 | 负责的功能 |
| --- | --- |
| TapComfy 客户端 | 招募与申请、补充资料、申请状态、推广码/链接、邀请客户、佣金明细、提现申请、转消费余额、历史记录 |
| new-api 后端 | 验证资格和归属、保存申请、读取配置、按支付事实计算佣金、资金占用和结算、按用户权限提供数据 |
| new-api admin | 申请审核、伙伴与规则管理、佣金查询、提现待办、标记已打款、驳回及备注 |
| 系统外 | 对私支付宝和对公银行账户的实际付款，由管理员独立完成 |

客户端只提交申请、金额、收款资料等用户输入，不决定谁能获得佣金、应发多少或是否结算成功。业务规则由 new-api 执行，避免客户端与后台各算一套。

**组织方式：同一服务中的独立业务模块。** 延续现有 `/api/tapcomfy/v1` 扩展入口，增加合作伙伴相关的用户接口和 admin 接口，沿用项目权限、响应与分页约定。合作伙伴资料、配置、佣金明细、提现和划转记录采用独立存储；保持现有 model/service/controller 分层，不让通用充值逻辑依赖 HTTP 控制器，也不为此另起微服务、消息平台或 Task Plugin。

**需要修改现有代码的接入点：**

| 接入点 | 预期改动 | 边界 |
| --- | --- | --- |
| 路由与模型初始化 | 注册新增 API 和业务数据表 | 新增接口，不重定义旧接口语义 |
| 充值完成 | 在当前启用的支付渠道成功入账路径接入统一佣金记账逻辑 | 基于可靠支付成功事实；重复通知/补单不能重复返佣，各渠道需明确实际付款金额与币种 |
| 佣金转消费余额 | 通过受事务保护的钱包入账路径增加消费额度，并记佣金扣减和划转流水 | 保留钱包限额、缓存同步和重试防重；不能用互不关联的两次写入完成划转 |
| 管理后台入口 | 加入合作伙伴与提现管理的路由、菜单、页面 | 不在 new-api 用户钱包再建设一套 TapComfy 客户端页面 |
| 邀请归属（优先复用） | 使用现有邀请码和 `InviterId` 关系 | 若引入可编辑码/历史别名才评估解析入口的局部调整，不重做注册登录 |
| 订阅（后续范围） | 按未来确认规则接入订阅付款事件 | 不把同步生成的 TopUp 再计一次，也不把余额买订阅当新付款 |

不能承诺零侵入：支付完成、钱包入账、路由和数据库初始化确实需要宿主接入；付款来源也可能需要补充记录字段。目标是将新业务集中在独立文件和数据表，现有流程只保留少量明确调用点。现有充值路径不完全统一，因此不能在实施前承诺只改一个函数。

充值成功与佣金记账之间需要可靠的一致性策略。实施时根据现有事务边界选择同事务记录或可恢复的记账方式，不能在 HTTP 回调返回后随意追加一次可能丢失的内存操作。此要求不意味着首版必须引入消息队列。

佣金账户独立于旧 `aff_quota` 注册奖励及用户消费钱包。旧注册赠送不会自动变成可提现现金。佣金转余额完成后，余额按现有消费机制使用；不把返佣计算加入模型转发、上游适配器、逐请求计费或任务插件。

接口清单、字段、币种和状态契约确认后，先在 new-api 完成后端与 admin，再按契约对接 TapComfy 客户端。后续上游同步时主要关注上述有限接入点，而不是在大量通用文件中散落合作伙伴判断。

## 13. 首版开发契约（以此为准）

用户要求：金额跟随现有后台配置，不另设固定汇率；new-api 管理端仅中文；不用 computer；各自在仓库内开发直到完成。new-api 协调者负责后端/Admin，Orca worker 负责 TapComfy。

### 金额

复用已有 `QuotaPerUnit`、`QuotaDisplayType`、`USDExchangeRate`、自定义展示符号/倍率，内部佣金使用整数 `*_quota` 记账（1 USD 现金对应 QuotaPerUnit，不是按客户获赠额度返佣）。实际付款 CNY 按付款时 USDExchangeRate 归一为美元现金；USD 原值归一。已记账历史不因更改设置重算。`Money` 在 Stripe 中是消费额度，禁止用其当实付；通过已验签支付事件保存实际金额币种。

提现表单按 `cash_currency=CNY` 展示支付宝/国内对公实际人民币到账金额，`cash_exchange_rate` 复用已有 USDExchangeRate。佣金概览使用已有钱包展示设置。转消费额度自动沿用 TapComfy 当前支付宝充值单价 AlipayNativeUnitPrice 和用户充值分组倍率（无套餐折扣），不再提供支付渠道选择：佣金美元现金 × USDExchangeRate ÷ (AlipayNativeUnitPrice × 用户分组倍率) × QuotaPerUnit。后台调价自动生效；申请记录保存当时价格，过时报价要求刷新。保留 `balance_price_source='alipay_native'`、`first_topup_only=false` 响应字段以兼容已有客户端，两项均不再可配置。CNY/USD 实付充值的返佣不受支付渠道限制。TOKENS 只用于展示，不能误标为现金。

### 共享接口

前缀 `/api/tapcomfy/v1`，沿用已有登录机制。响应 `{success:true,data:...}`，错误 `{success:false,message:string,code:string}` + 4xx/5xx。客户端分页 `?page=1` 每页20（Admin 可额外传 size，范围1–100），`{items:[],total,page}`，时间 Unix 秒。

`GET /partner`: `{application:Partner|null,config:Config,money:Money,summary:Summary,referral_code:string}`。
`POST /partner/application`: `{channels,links,plan,contact,evidence,notes}` 全部 string；渠道/说明/联系必填，其余可选；自由渠道，资料按需补充；links/evidence 是可选多行 HTTP(S) 链接，不做公开截图上传。状态未申请/needs_info/rejected 可提交，返回 Partner。
`GET /partner/invitees`: 分页 `{user_id,username,created_at,topup_count,topup_quota,commission_quota}`，只有本人的客户，不返回消耗。
`GET /partner/commissions`: Commission 分页。
`GET /partner/payouts`: Payout 分页，包含提现和划转。
`POST /partner/payouts`: `{request_id,kind:'alipay'|'bank'|'balance',amount:string,exchange_rate:string,recipient_name:string,account:string,bank_name:string,company_code:string}`。amount 以人民币元为单位（balance 也输入要用掉的人民币佣金）；exchange_rate 传 money.quote 字符串，整个报价版本用于过期校验。request_id UUID，新操作新ID，失败重试同参数同ID；不要持久化收款信息到 localStorage。balance无需收款资料；alipay姓名账号必填；bank企业名称、账号、开户行、统一社会信用代码必填。返回 Payout。
推荐码复用既有 aff_code、客户端现有 aff 注册链接；首版不修改邀请码，不改注册链路。

Partner: `{user_id,status:'pending'|'needs_info'|'approved'|'rejected'|'suspended',channels,links,plan,contact,evidence,notes,review_note,created_at,updated_at,approved_at,reviewed_by,available_quota,reserved_quota,earned_quota,withdrawn_quota,transferred_quota}`。
Config: `{balance_price_source:'alipay_native',enabled:boolean,commission_bps:number,duration_days:number,first_topup_only:false,min_payout_cents:number,alipay_daily_limit_cents:number,bank_single_limit_cents:number}`。bps 1000=10%，天数0长期，限额0不限，默认关闭，默认比例0等待管理员设置；限额单位为现金人民币分。
Money: `{quota_per_unit:number,currency:string,currency_symbol:string,exchange_rate:string,cash_currency:'CNY',cash_exchange_rate:string,credit_price:string,quote:string}`。exchange_rate用于概览展示（USD/CNY/CUSTOM/TOKENS语义同wallet）；credit_price为每1消费美元额度所需人民币佣金（含用户充值分组倍率），quote为服务端不透明报价字符串；客户端原样回传。输入人民币 amount 对应消费额度 = amount/credit_price，显示为额度而非真实美元现金。可提人民币最大值向下截断到分。
Summary: `{invited_count,topup_count,topup_quota,earned_quota,available_quota,reserved_quota,withdrawn_quota,transferred_quota,alipay_remaining_cents:number|null}`，null不限。
Commission: `{id,partner_id,user_id,topup_id,paid_amount:string,paid_currency:string,exchange_rate:string,topup_quota,commission_bps,commission_quota,reason:string,created_at}`，每订单唯一，允许0佣金用于完整充值统计。
Payout: `{id,user_id,request_id,kind,amount:string,currency:'CNY',debit_quota,status:'pending'|'paid'|'rejected',recipient_name,account,bank_name,company_code,exchange_rate,credit_price,quota,review_note,reviewed_by,created_at,completed_at}`；quota仅划转，debit_quota为扣除佣金。

规则：有效期从 max(客户注册,伙伴首次获批) 起算；有效期内每次外部真实充值均可返佣；获批前不补；配置修改影响后续付款；暂停停止新增佣金保留资金出口；首版无等待期无手续费，订阅以后接入。充值统计仅累计计划开启后、邀请人已有申请的可靠付款记录，不伪造历史实付；并明确展示统计范围。注册奖励不算现金佣金。

### 开发与验证记录（2026-09-29）

首次完成验证时，代码位于两个仓库各自的 `codex/feature/partner-referrals` 分支；以下记录为当时的实现及测试结果。

- new-api：独立 Partner / PartnerCommission / PartnerPayout 三表及接口、中文 `/partners` 管理页；TopUp 增加实付金额、币种、测试支付标记，支付成功事务调用佣金记账。未修改 relay、模型定价、任务插件和注册登录机制。
- TapComfy：个人中心“合作伙伴”，申请与审核状态、推荐链接、客户充值次数/金额、佣金记录、提现及消费余额划转，通过已有 Rust 登录代理访问接口。伙伴不显示消耗统计。
- 申请材料使用自由文本和可选 HTTP(S) 资料链接，审核时按需补充。没有新增图片托管及企业认证系统。
- 佣金账本与旧注册赠送 `aff_quota` 隔离，消费划转不触发二次返佣。提现申请即占用，人工付款确认仅结算占用，驳回释放。
- 真实付款按验签事件记账；易支付使用验签表单 money、Stripe 使用 amount_total、Creem 使用 amount_paid、Waffo/Pancake 使用回调实际金额。原生支付宝沿用核验后的订单实付金额。测试支付不返佣。手工补单缺少实付事实时不根据消费额度猜测现金佣金。
- 目前原有后台只提供人民币/美元汇率，故返佣支持 CNY/USD。其他币种付款仍正常充值，记录原实付及 `reason=unsupported_currency`，明确显示“该付款币种未配置返佣汇率，未计佣金”；不猜汇率、不将消费额度当实付。不自动补发历史未计佣金记录。
- 停用计划或暂停伙伴均保留已有余额的提现/划转；全局停用期间不新增充值佣金记录。规则变更不重算旧账。兑换操作锁定提交时汇率、售价和报价，重试返回原申请。
- 默认关闭、默认佣金比例为 0；管理员先设置比例/期限/提现限额，再开启。资料补充/驳回/暂停必须填写原因。付款页展示收款资料与金额并二次确认，不接支付宝或银行转账 API。
- 查询只接受当前登录身份；Admin 路由复用现有管理员鉴权。既有管理端登录使用 Authorization Bearer，不新增 cookie 鉴权入口。接口设置禁止缓存。

稳定错误码：`partner_invalid`（400）、`partner_state` / `partner_funds` / `partner_quote_changed` / `wallet_limit`（409）、`partner_not_found`（404）、`partner_unavailable`（500）。网络失败/5xx 等未知结果必须保留原参数和 request_id，核对记录后重试，不能重新生成申请。
